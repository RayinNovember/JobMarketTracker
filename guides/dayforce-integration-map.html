Page 1 · The main pattern

Ingest, store, distribute

One program copies Dayforce into a SQL database. Eight integrations then read that copy and send files out. If the copy goes stale, they keep running but send stale data.

Layered finding · PaySummary-Issue Handoff & Diagnosis

Pay Summary: what the handoff says vs. what the evidence shows

The handoff brief was written from the source code alone. The VM folder, its logs and the live SQL tables tell a different story.

Handoff brief

Problem

tAssociatePaySummaryRecord stopped getting rows, while the nightly job reports success. A silent no-op, not a crash.

Root cause it names

A runsettings.json on the VM turns off the "everything on" default, and the settings file has no way to switch Pay Summary back on, so the step logs "Skipping Processing Pay Summary" every night.

Evidence · VM + SQL

The flag is on

  • The VM has no runsettings.json, only runsettings.json.bak, so the default "everything on" path applies.
  • Full-run logs print "Process Pay Summary: True", and "Processing Pay Summaries Started" appears 879 times since 2024.

What actually happens

  • Some run logs end at "Processing Pay Summaries Started" with no "Done.": 7/1, 7/22, 8/5, 8/19, 9/9 and 9/16. The VM troubleshooting summary calls this normal for good runs. Whether those runs finished the later steps is unconfirmed.
  • Then the 9/16–9/25 outage stopped everything (step 1).
  • SQL now: writes resumed 9/26; the latest was 10/27 at 14:42 (data through 10/26). Nothing was written on 10/28 or 10/29.

Flows that write into Dayforce

These run the opposite way: outside data goes into Dayforce through its API. Their changes reach the SQL mirror only when DayforceProcessor next copies Dayforce in.

JobviteProcessor

One JobviteProcessor run, in order

Its own database is Jobvite on the same SQL server. Its folder was copied from the VM on 30 Oct (VM-JobviteProcessor, 11,060 logs since Jan 2024). It runs as two scheduled jobs: the main run (steps 0–7) at 06, 08, 10, 12, 14, 16, 18 and 23, and the user sync (step 8) on its own at 09, 13 and 15. Within a run, any step that throws ends the run, and nothing after it happens.

Page 3 · Exception 2

The Jobvite webhook

Jobvite pushes a message the moment a candidate or job changes. This path doesn't touch Dayforce or the SQL mirror, but it does write into the same Jobvite database that JobviteProcessor uses.

WebhookEndpoint

One webhook message, in order

An Azure Function app. It runs whenever Jobvite calls it, not on a schedule.

  1. 1
    Receive the call and check the signature Separate addresses for candidate and job events. A missing or wrong Jobvite signature is rejected.
  2. 2
    Save the raw message Stored as-is with "not processed yet", so nothing is lost if a later step fails.
    tJobviteRawtDayforceWebhookData
  3. 3
    Put a message on the Service Bus queue Only the saved row's ID goes on the queue. A failed message goes back on the queue to retry.
  4. 4
    Fetch the full record from the Jobvite API The queue watcher looks up the complete candidate or job.
  5. 5
    Update the Jobvite database Candidate, application workflow status or requisition. Newest workflow row today: 10/29 at 18:24.
    tCandidatetCandidateApplicationtCandidateApplicationWorkflowStatustRequisition
    Shared tables

    JobviteProcessor's step 3 writes to these same tables. Its log shows the clash is with one application ID, pzjsNywa, which differs only in letter case from a second application on the same candidate (see page 2, step 3). The webhook itself stored both rows without error.

  6. 6
    Mark the raw message processed
Notes
  • The webhook only covers candidates, applications and jobs. Onboarding (new hire records and SSNs) comes only from JobviteProcessor step 4, which is why only the onboarding tables went stale.
  • A Dayforce/All address exists in the same app but only answers "OK" and saves nothing.
  • Failures email an alert through the HVE email service.

1 · A2

Requisition step crashes on every run

Active since 14 SepCause confirmed

Problem

JobviteProcessor stops at its first data step, so nothing after it runs: candidates, onboarding, hires into Dayforce, the report, and the refresh of locations and workflow statuses.

What happened

Req #20726 "Community Manager" (oCPwAfwh) has a location ID (CnV9Vfw6) but no location list. It was harmless as a draft from 21 Jul; when it was closed on 14 Sep Jobvite started sending it. The code assumes every job has a location list and crashes at JobviteLibrary.cs:685. The window stays stuck at 10 Sep, so it repeats every run. The webhook fails on the same job.

Fix

  • Jobvite admin · no codeOpen #20726, check location CnV9Vfw6, then give it a valid location or delete it.
  • Code + deployTreat a missing list as empty at lines 668 and 685 and in RequisitionLocation.cs:25.
  • After the admin fix, expect the run to stop at issue 2 next.
2 · A3

Candidate step fails on two applications that differ only in letter case

Hidden behind issue 1Very likely

Problem

From 26 May to 10 Sep every main run failed at candidates. It will come back as soon as issue 1 is fixed.

What happened

Candidate eZFOCtw2 applied for two jobs and got application IDs pzjsNywa and pZjsNywA. The database treats case as meaningful and stores both; the program is set to ignore case (JobviteContext.cs:107-126), merges them when reading, thinks one is missing, and its re-insert is refused as a duplicate.

  • Confirm in the deployed JobviteLibrary.dll first (needs a decompiler).

Prevent: fixes that remove the cause

Make the code fail small

Developer
  1. One bad record should skip that record and be reported, not stop the whole run (requisitions, candidates, user sync).
  2. Treat missing lists as empty everywhere the code reads API data.
  3. Compare IDs the same way the database does (case-sensitive).
  4. Drop the hardcoded list of 30 statuses; fetch all and map unknown ones.
  5. When a status or location is unknown, refresh the list and retry instead of rejecting the message.
  6. Log the real error when Key Vault or Entra fails, instead of hiding it.

Keep the mirror honest

Developer · data owner
  1. DayforceProcessor should delete work assignments Dayforce no longer has.
  2. One-time clean-up of existing leftover rows, after measuring how many there are.
  3. A weekly check for employees with zero or several current primary assignments in the mirror.
  4. A periodic spot-check of a few employees: mirror against the Dayforce screen.

Coordinate Jobvite changes

HR · Jobvite admin · IT
  1. Agree that new workflow statuses, screening forms, locations, templates or webhook settings are flagged to IT before going live.
  2. A short checklist for each change: does the integration know the new value, are the webhook events still on, does a test applicant reach SQL?
  3. Avoid closing or using jobs that have no location.

Secrets, deploys and ownership

IT
  1. Switch the VM to a managed identity, or at least set expiry alerts on the Azure app secret and the Entra credential.
  2. Deploy only from committed code, through the existing azure-pipelines.yml or the written runbook, and record which commit is live.
  3. Stamp a real version number in each log header (today every build says 1.0.0.0).
  4. Name an owner for the integrations and keep this map current.
