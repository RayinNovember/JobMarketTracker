Two jobs, one database

The project has two flows that meet in Postgres. The monthly pipeline puts postings into the database. The LLM skills module reads them back, asks Claude about each one and writes skills alongside them. Blue boxes are outside services and SQL views. Dashed boxes are not built yet.

Tools vs. scripts

The same split runs through the whole repo. A file in core/ defines things and doesn't run anything by itself. A file in projects/linkedin_jobs/ is one you run with uv run python -m …. It imports the tools and does the work.

One run of run.py, in order

Started by GitHub Actions on the 15th, or by you with uv run python -m projects.linkedin_jobs.run --limit 25. All the database work happens on one connection, opened once.

  1. 01
    Start up and read settings core/settings.py loads .env on your machine. On GitHub the same names come from repository secrets. parse_args reads --limit and --searches, which override config.yaml. A ThemeTagger is built from themes.yaml.
    config.yamlthemes.yaml.env
  2. ↳
    Shortcut: --retag or --rehash These re-apply themes.yaml or recompute job_hash on every stored posting, then exit. Nothing is scraped. Use them after you edit themes or change the hash.
  3. 02
    Open a run in the log runlog.start_run inserts a row with status running and the parameters, commits it right away, and returns a run_id. If the job crashes later, this row still shows that the run happened.
    core.run_log
  4. 03
    Scrape each search term scrape.run_search converts the config into the actor's input, starts the Apify actor, waits for it to finish, then reads its dataset. It returns the items and the cost in USD. If one term fails, the error is recorded and the other terms still run.
    Apify · curious_coder/linkedin-jobs-scraper
  5. 04
    Transform: merge, then one clean row per job merge_items keeps each job ID once, even if two searches found it, and remembers which terms found it. It also removes personal data about the poster. to_row maps fields, parses salary text into min, max and period, computes content_hash and job_hash, and tags themes.
  6. 05
    Load: raw copy, then dedup upsert, in one transaction insert_raw saves the scraper's output as JSON, one row per job per run, so the clean table can be rebuilt without scraping again. upsert_postings loads the rows into a temporary stage table, then runs insert … on conflict (job_id) do update. A new job gets a new row. For a known job it refreshes the fields, merges the search terms and increases last_seen_at and times_seen. xmax = 0 tells new rows from updated ones.
    jobs.raw_postingsjobs.postings
  7. 06
    Close the run finish_run records the status (succeeded, succeeded_with_errors or failed), the row counts, the cost and any errors. It rolls back first, so a failed transaction can't stop the log from being written. The exit code is 1 only if the run failed, which turns the GitHub run red.
    core.run_log

Three ways to say "the same job"

LinkedIn reposts roles under new IDs and gives a multi-city role one ID per city. Each row stores three identities so the views can collapse these duplicates without deleting anything.

KeyBuilt fromGroups together
job_idLinkedIn's IDThe same posting seen in several monthly runs. This is the primary key of jobs.postings.
content_hashcompany + title + location + descriptionA repost: the same role in the same place under a new ID
job_hashcompany + title + descriptionA repost or a multi-city role. postings_dedup groups on this one.

Two passes: build a list, then tag against it

Claude reads one posting at a time, and SQL does the counting. If Claude named skills freely in every posting, the same skill would get several names, and those can't be counted together. So Pass 1 names skills freely in a sample and merges the names into one list. Pass 2 tags every posting, allowing only names from that list. All three kinds of request go through one Claude object, which sets the model and the JSON schema and keeps a running cost.

Pass 1: skill_discover.py, in order

Run it with uv run python -m projects.linkedin_jobs.skill_discover --sample 20 first (a few cents), then without --sample for the full 500 (about $0.15).

  1. 01
    Sample postings Picks random rows from jobs.postings_dedup (one row per role, so reposts don't skew the sample) that have a description.
    jobs.postings_dedup
  2. 02
    extract_open on each posting Sends the title and description, cut at 8,000 characters, with an open schema. Any skill name is allowed, but the category must be one of four. If a request fails, that posting is skipped and the loop goes on.
  3. 03
    Count phrases with Counter The key is (lowercased phrase, category). Phrases go into a set before counting, so a wordy posting counts each phrase once.
  4. 04
    build_list: one bigger request Sends the 400 most common phrases with their counts, at effort="medium". Claude merges synonyms into 40 to 60 skills, each with a name, a category and a one-sentence definition.
  5. 05
    Write the draft, then you edit it Writes skills_draft.yaml, sorted by category. You merge, split and sharpen it by hand, then save it as skills.yaml. The definitions matter: Pass 2 puts them in its prompt to decide what counts as each skill.
    skills_draft.yamlskills.yaml

Pass 2: skill_tag.py, what it will do

Guide section 12.6. You'll run it on every posting once, then monthly on new postings only.

  1. 01
    Load skills.yaml into SkillTagger The constructor builds the system prompt (skills grouped by category, with definitions) and a closed schema in which skill must be one of your names.
  2. 02
    sync_skills: make jobs.skills match the YAML Adds new skills, updates categories and definitions, and deletes skills you removed. Changing a category only touches this table, so no posting needs re-tagging.
    jobs.skills
  3. 03
    Pick untagged postings Postings with other_skills is null, newest first. --retag TEXT and --retag-all set this column back to null so those postings get tagged again.
  4. 04
    Tag each posting and write it tag() returns {skill: level} plus up to 5 new phrases. For each posting the script deletes its old skill rows, inserts the new ones and stores other_skills, even when it's empty ({}). It commits every 50 postings and stops after 5 failures in a row.
    jobs.posting_skillsjobs.postings.other_skills

Two things fixed before Pass 2

Your SkillTagger differs from the guide in two places. Pass 1 doesn't use SkillTagger, so neither one breaks skill_discover.py. Both would have failed the first time skill_tag.py ran. Both are now fixed to match the guide.

fixedself.names was a set

core/skills.py:288 builds {s["skill"] for s in skills}, and the schema uses it as "enum": self.names. A set can't be converted to JSON, so the first request would have raised TypeError. It's now a list: [s["skill"] for s in skills].

fixedclaude was required in SkillTagger.__init__

The guide's signature is claude: Claude | None = None with self.claude = claude or Claude(). skill_tag.py calls SkillTagger.from_yaml(path) without passing a Claude. It now defaults the same way.

minorANTHROPIC_API_KEY isn't in settings.REQUIRED

settings.get still raises a clear error if the key is missing. The only effect is that python -m core.settings won't report on it.
